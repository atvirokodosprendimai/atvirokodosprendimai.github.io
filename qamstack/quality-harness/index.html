Quality HarnessKnow when your AI agent's “done” is really done.

A free plugin for Claude Code. When your agent says the work is finished, Quality Harness runs your tests itself and writes down what really happened. If they didn't pass, the work isn't done, and the commit is blocked until they do.

What to expect

What changes after you install it.

You keep working the way you do now. Quality Harness sorts each request and handles the checking. Most days look like the first card.

Everyday fixes

Your tests run before anything is committed

  1. You ask for a fix. The agent makes it, as usual.
  2. Quality Harness runs your project's tests. It finds your usual test command on its own, or you tell it which one to use.
  3. If the tests haven't passed, the commit is blocked until they do.

Bigger decisions

A written plan first, then proof for each step

  1. The agent writes the decision down. You read it and approve it.
  2. Each step gets one command that proves it works.
  3. Quality Harness runs that command and saves the result in your project. A step can't be marked done without it.

What you'll notice

A little more effort, a lot less guessing

  1. The agent takes more steps: about 2.3 times as many in the project's own measurement. Most of the extra is cheap, cached input.
  2. You're asked what would prove the work is done, before it starts.
  3. A few lines added to your files. You commit them along with the change.

Why it matters

Your agent says “done”. Did it actually check?

Often it didn't, and you can't tell from the message. Researchers have measured it: when an AI coding agent reports on its own work, the report is wrong more often than you'd think, and another AI can't reliably catch it. Several tools appeared this year to deal with this. Below is what makes this one different.

75.8%

of failed tasks were reported as a success. The agent said “done”; the result said otherwise.

Five AI judges tried to spot these. None could do it reliably: the best scored 0.65, where 0.5 is a coin toss. From Confident Closing to Silent Failure, arXiv 2606.09863, June 2026.

“Agent self-reports should therefore be treated as claims to verify against the environment, not as evidence of their own reliability.” Self-Reports Are Not Verification, arXiv 2609.00652, 1 September 2026.

What's different

Proof you can check, kept in your project.

Four things set it apart. Other tools do one or two of them; none does all four. Compared on 2026-09-24, from each tool's own documentation.

1 · kept in your project

The proof lives next to your code

Every finished step gets one line: when it ran, on which version of your code, which command, and whether it passed. The tool writes it, not the AI. It's saved in your project, so anyone can read it next week or next year. If it says it passed, it passed.

Elsewhere: a message on screen, a verdict from someone else's server, a report handed back to the AI, or a receipt that stops counting when the session ends.

2 · tied to the exact test

Change the test, and the old proof stops counting

Each line carries a fingerprint of the exact command that ran. Change the command and every earlier result stops counting, so old proof can't be passed off as an answer to a new question.

Elsewhere: a receipt that counts only while the current session vouches for it.

3 · a program decides

The AI can't talk its way to “done”

A plain program reads the saved results and won't accept “done” without a passing one. It gives the same answer on your laptop and in your build pipeline. No AI is asked.

Elsewhere: one tool compares the AI's last message with what happened in that turn; some block a commit until tests run, as this one does. None refuses a “done” saved in your project when your build pipeline checks it later.

4 · tests that can fail

It checks that your tests can catch a bug

A test that always passes looks like safety and isn't. Quality Harness breaks your code on purpose, runs the test, puts the code back, and records whether the test noticed.

Elsewhere: the AI is told to watch a test fail first. No other tool breaks the finished code to check that the test notices.

How it works

Four small programs. Each one says pass or fail.

You tell it how your project runs its tests, or it finds out. For bigger work, each step gets one command that proves it. Everything else is a program reading those files.

0 · before every commit

qh-check runs your tests before a commit

On every change. It runs your project's tests and remembers the result. Until they've passed, the commit is blocked. Even a quick fix can't go out untested.

$ qh-check   # runs the declared check, exits with its code
{…,"command":"npm test","exit":0,"verdict":"passed",…}  → checks.jsonl, abbreviated

1 · write down the result

adr-verify runs the proof and writes it down

It runs the step's proof command itself, then adds one line: the date, the code version, the result, the command, and its fingerprint. Change the command and earlier lines stop counting. Nobody edits these lines by hand.

- 2026-09-23 · ac1d286* · exit 0 · `python3 -m unittest …`
  · acceptance-sha256:b43e2374…ec4405 · ms:52

2 · refuse “done” without proof

adr-lint says no to an unproven “done”

If a step is marked done but has no passing result behind it, this program refuses it. Everything else it reports is advice, and it tells you which is which.

README.md: T1 marked done but its Verification Log
has no exit-0 entry — run adr-verify, don't hand-declare

3 · check the test can fail

adr-verify --mutant breaks your code on purpose

It breaks the code, runs the test, and puts the code back. If the test still passes, that test isn't protecting anything, and now you know.

- 2026-09-23 · ac1d286* · mutant killed · exit 1
  · `duration.py` · from `int(text)` to `0` · why …

Quality Harness is built with itself: its own tests run on every change, and bash scripts/selftest.sh shows today's numbers

Under the hood

What gets written down, and who writes it.

Every check is a plain program reading files in your project. Same files, same answer, on any machine. The AI does the work; it never gets to mark it as passed.

  1. You write

    One proof command

    In the step's file, under ## Acceptance. One line that decides whether the step is done. The tool never guesses it.

    python3 -m unittest -v test_duration

  2. The tool runs

    adr-verify runs it

    A real program, not the AI. Whatever the result is, that's the answer. If it couldn't run, it says so instead of passing.

  3. The tool writes

    One line of proof

    When, which code version, the result, the command, its fingerprint, how long it took. Added, never edited. Broken down below.

  4. A program reads

    adr-lint checks it

    A “done” needs a passing line whose fingerprint matches today's command. Nothing else counts.

  5. The answer

    done standsa passing line, same command done refusedno passing line, or the command changed UNRUN · PARTIAL · UNPROVENnothing was checked; never a pass

you write it the tool writes it a program reads it the answer

one line of proof, piece by piece
- 2026-09-031 · 1d9381f*2 · exit 03 · `python3 -m unittest -v test_duration`4 · acceptance-sha256:b43e2374…5 · ms:756
  1. 2026-09-03When it ran. The date the check actually ran.
  2. 1d9381f*Which version of your code. The star means there were unsaved changes too, and that's recorded.
  3. exit 0The result. 0 means it passed. It's the program's own answer, not a summary.
  4. `python3 -m unittest …`The command. Exactly what was run, so anyone can run it again.
  5. acceptance-sha256:…Its fingerprint. Change the command and every earlier line stops counting. Old proof can't answer a new question.
  6. ms:75How long it took. Handy when something that took a second starts taking a minute.

Your files stay yours. The tool only adds lines under two headings, ## Verification Log and ## Mutation Log, and never creates them. Nobody, person or AI, edits those lines by hand.

Getting started

Six habits that make it work.

The tool is small. These habits are what make it pay off. Here's the short version, in the order you'll meet them.

  1. One command, once, at the start

    Type it in your main session. It sorts the work for you: a bug goes straight to a fix, a bigger decision gets written down first. Use it for real work, not quick questions.

    /quality-harness:work

  2. Say how you'll know it works, before you start

    Each step gets one command that decides whether it's done. Writing it first is the one extra step, and it's worth it: if you can't say what would prove the work is done, the work isn't clear yet.

    ## Acceptance
python3 -m unittest -v test_duration

  3. Commit the proof with the change

    When the tool adds its line, commit it along with the work. Never edit those lines by hand. If you change the proof command, run it again.

    [adr-verify] WROTE this entry into …/T1.md
# commit it with the work it evidences

  4. In your first week, break one thing on purpose

    Pick the code you'd least like to see break without anyone noticing. The tool breaks it, runs the test, and puts it back. “mutant killed” means your test works. Save the full run for your build pipeline.

    adr-verify T1.md --mutant duration.py \
  --from 'int(text)' --to '0' \
  --why 'the test must notice'

  5. UNRUN, PARTIAL and UNPROVEN mean “not checked”

    The tool tells you when it couldn't check something, instead of pretending it passed. Treat these as not passed, every time.

  6. If a commit is blocked, run your tests

    Once your project has tests the tool can find, a commit is blocked until they pass. Running qh-check is the whole fix. Prefer a warning? Set "publish": "warn" in .quality-harness.json.

    qh-check
# your check runs and is recorded

Lost track? node "$(qh-root)/scripts/work-next.mjs" tells you what's waiting and why. Written decisions are for choices you'd regret undoing; a one-line fix is just a fix. Leave the advanced features alone until you need them.

Good to know

Three design choices, and what it costs you.

Each one is a deliberate decision, recorded in the project. The last one is the price.

  • Built for Claude Code. The automatic checks run inside Claude Code. Cursor, Codex, Zed and Claude Desktop can run the checks and use a read-only connection (qh-mcp) that tells you when something's off. Saving proof needs a terminal, because only a program that actually ran can report a result.
  • It blocks one thing, on purpose. Once your project has tests the tool can find, a commit is blocked until they pass (ADR-061). A warning the AI shrugs off still gets committed, so this one is a block. Everything else is advice.
  • It has its own format for decisions. Decision records in other formats (MADR, Nygard) are left alone, not judged (ADR-038). New decisions written with /quality-harness:adr-write get the proof lines.
  • The price. More steps: about 2.3 times as many in the project's own measurement, though most of the extra input is cheap, cached reads. You write the proof command yourself; the tool won't guess it. The full “break it on purpose” run takes about forty minutes, so it belongs in your build pipeline. The automatic checks run on every edit, and claude plugin details quality-harness shows how much context it uses.

Questions

Common questions.

Isn't this just “write tests”?

No. Tests check whether the code is right. This checks whether the claim that the work is done has a real test run behind it, and refuses the claim when it doesn't.

Why not let the AI check its own work?

Because the AI is what's being checked. In one study, five AI judges couldn't reliably spot false “done” reports (0.65 at best, where 0.5 is a coin toss; arXiv 2606.09863). Here, an AI can flag things, but only a program can record a pass.

Will it get in my way?

In one place: a commit is blocked until your tests pass, and you can turn that into a warning. Everything else is advice, and it tells you what to do next.

Can I use it outside Claude Code?

Yes. The checks are ordinary Python and Node programs. Run them from any terminal, script or build pipeline, with no AI involved.

Does it work with my language?

Yes. The proof command is whatever you'd normally type: go test ./..., pytest -k, npm test. It doesn't guess one for you.
