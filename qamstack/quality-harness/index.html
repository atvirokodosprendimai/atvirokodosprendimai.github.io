Quality Harness“Done” is a recorded run, or the check refuses it.

A Claude Code plugin with two mechanisms. A commit is refused until your project's own check has passed on the tree. A task backed by a decision record is done only when a tool ran its acceptance command and wrote the exit code, the commit and a digest of what ran into the record. You merge evidence, not summaries.

Why now

Your agent says “done”. The message looks the same whether it checked or not.

Every coding agent reports its own status. The research measured how often that report is wrong, and whether another model can tell. It is the most common way coding agents fail, and it is the failure you cannot see from the transcript. A category is now forming around it: at least five Claude Code tools exist whose whole pitch is checking the agent's own claim. They are compared below.

75.8%

Of failures among self-assessing coding-agent trajectories were false success: the agent said done, the environment said otherwise.

No LLM judge in the study caught it reliably; none of five exceeded AUROC 0.65. From Confident Closing to Silent Failure, arXiv 2606.09863, June 2026.

4.8–9.3×

How far LLM operators overstated their own success when every proposal received an exact outcome.

“Agent self-reports should therefore be treated as claims to verify against the environment, not as evidence of their own reliability.” Self-Reports Are Not Verification, arXiv 2609.00652, 1 September 2026.

22.58%

Of misalignment episodes in 20,574 real sessions were inaccurate self-reporting, and that share is rising while the others fall.

91.49% of visible resolutions needed the developer to step in. How Coding Agents Fail Their Users, arXiv 2605.29442 v2, 31 August 2026.

figures as published · retrieved 2026-09-23 · the full reading list is in the repository under docs/research/

What you gain

A “done” you can merge without reading the diff twice.

Three things change on day one. The third is measured against a baseline, which is the only way a claim like that should be made.

Evidence, not summaries

Every finished task carries a line a program wrote

Date, commit, exit code, the exact command, and a digest of it. No model wrote any of it. If it says exit 0, a process exited 0. You stop re-running the tests yourself to find out whether the agent did.

Tests proven able to fail

A green suite that cannot go red is named, not trusted

The mutant run breaks your code on purpose, re-runs the check, restores the file and records whether the test noticed. A test that passes no matter what looks like safety and is not. Now it has a name in the log.

Decisions where the code lives

The next session reads why, not just what

Why something was built this way sits in a record next to the code, not in a chat log nobody can search six months later. An agent that consults the record before writing a new one stops relitigating what you already decided.

Measured, with a baseline

Every eval case runs with the plugin and without it, five runs per arm. Where the subject is verification, the baseline scores zero.

How it works

Four ordinary programs. Read their exit codes.

Your project declares one check. A record holds a decision; a task holds one shell command that decides whether the work is done. Everything else is a program reading those files.

0 · gate the commit

qh-check runs your check and holds the door

Every day, on every change. It runs the check your project declared, records the result against the current tree, and until a pass is recorded a command that names commit or push is refused. A bug fix with no record still cannot be published unchecked.

$ qh-check   # runs the declared check, exits with its code
{"command":"npm test","exit":0,"verdict":"passed", …}  → checks.jsonl

1 · record the run

adr-verify runs the check and writes the line

It runs the task's ## Acceptance command, then appends the date, the git sha, the exit code, the command and a SHA-256 of it. Change the command and every earlier line stops matching. Logs are never edited by hand.

- 2026-09-23 · ac1d286* · exit 0 · `python3 -m unittest …`
  · acceptance-sha256:b43e2374…ec4405 · ms:52

2 · refuse a bare claim

adr-lint fails a done with no line behind it

A task index that says done while the task's log has no matching exit-0 entry is a blocking finding. Everything else the lint says is advice, and it says which is which.

README.md: T1 marked done but its Verification Log
has no exit-0 entry — run adr-verify, don't hand-declare

3 · prove the test can fail

adr-verify --mutant breaks the code on purpose

A green test proves little until something shows it can go red. The mutant run edits a source file, re-runs the check, restores the file, and records whether the test noticed. A survivor is a finding about the test.

- 2026-09-23 · ac1d286* · mutant killed · exit 1
  · `duration.py` · from `int(text)` to `0` · why …

the plugin runs this lifecycle on itself: its own tests and mutation campaign run in CI on every push, and bash scripts/selftest.sh prints today's numbers

The convention

One line, two files, and a word for not knowing.

Every gate is a deterministic reading of files in your repository. Same files, same answer, from any shell, with no model in the loop. A model routes the work; a model never writes a verdict. This is the whole vocabulary.

  1. You write

    One acceptance command

    In the task file, under ## Acceptance. One shell line that decides whether the work is done. The tool never guesses it.

    python3 -m unittest -v test_duration

  2. The tool runs

    adr-verify executes it

    A process, not a model. Whatever exit code comes back is the answer, and a check that could not run says so instead of passing.

  3. The tool writes

    One line into ## Verification Log

    Date, commit, exit code, the command, a digest of it, the duration. Appended, never edited. Taken apart below.

  4. A program reads

    adr-lint checks the claim

    It reads the task index and the log. A done needs an exit-0 line whose digest matches the current command. Nothing else is consulted.

  5. What comes out

    done standsan exit-0 line, digest current done refusedno line, or the command changed UNRUN · PARTIAL · UNPROVENnothing was measured; never a pass

you write it the tool writes it a program reads it the verdict

one verification log entry, taken apart
- 2026-09-031 · 1d9381f*2 · exit 03 · `python3 -m unittest -v test_duration`4 · acceptance-sha256:b43e2374…5 · ms:756
  1. 2026-09-03When it ran. The date the tool executed the command, not the date someone typed it.
  2. 1d9381f*Which commit. The star means the working tree was dirty at the time, and that is recorded too.
  3. exit 0What the process returned. If it says 0, a process exited 0. No summary, no paraphrase.
  4. `python3 -m unittest …`The command itself. Your ## Acceptance line, verbatim, so a reader can run it again.
  5. acceptance-sha256:…A digest of that command. Edit the acceptance line and every earlier entry stops matching. There is no way to keep old evidence for a new question.
  6. ms:75How long it took. Useful when a check that used to take a second starts taking a minute.

The files are yours and the entries are the tool's: a task file holds one ## Acceptance command and two empty sections, ## Verification Log and ## Mutation Log, which the tool appends to and refuses to create. Nobody, human or model, edits a log by hand.

Use it right

Six habits that decide whether it works for you.

The tool is small. The discipline is the product. Each of these is in the onboarding guide; this is the short form, in the order you will meet them.

  1. One command, once, in the main session

    It classifies the work and routes it: a bug goes straight to execution, a decision you would regret reversing goes through a record first. You do not have to know which. Not inside a subagent, and not for questions.

    /quality-harness:work

  2. Write the acceptance command before the code

    A task carries ## Acceptance: one shell line that decides whether the work is done. Writing it first is the tax, and it is the point. If you cannot say what would prove the work done, that is information about the work, not about the tool.

    ## Acceptance
python3 -m unittest -v test_duration

  3. Commit the evidence with the change

    adr-verify writes into your task file and tells you so every time. Those lines are the record; commit them with the work they prove. Never hand-edit a log. If you change the acceptance command, every earlier entry stops matching. Re-run it.

    [adr-verify] WROTE this entry into …/T1.md
# commit it with the work it evidences

  4. Add one mutant in week one

    Pick the code you would most hate to see silently broken. mutant killed is the answer you want; a survivor is a test that proves nothing. Run the full campaign in CI and at release, not on every edit.

    adr-verify T1.md --mutant duration.py \
  --from 'int(text)' --to '0' \
  --why 'the test must notice'

  5. UNRUN, PARTIAL and UNPROVEN are not passes

    They mean nothing was measured. The tool says so instead of reporting a clean result it never observed. Read them that way, and never let one through as green.

  6. When a commit is refused, run the check

    Once your project declares a check, a commit or push is refused until qh-check has passed on the current tree. That is the whole fix. "publish": "warn" in .quality-harness.json if you must.

    qh-check
# your check runs and is recorded

Lost the thread? node "$(qh-root)/scripts/work-next.mjs" reads the corpus and says which stage is waiting and why. Records are for decisions you would regret reversing; a one-line fix is a one-line fix. Leave specs, architecture lint and consensus alone until a problem calls for them.

What only this row has

The evidence is a line in your repository, bound to the command by a digest, read by a lint that refuses done, and paired with proof that the test could fail.

  1. It lives in the repo. Not a hook's console line, not a hosted verdict, not JSON handed back to the agent. A line in the task file, committed with the work, readable in a year.
  2. The digest binds it to the command. Change the acceptance command and every earlier entry stops matching. A receipt vouched for by a session expires with the session; this one expires with the question.
  3. A program refuses done. adr-lint reads the task index and the log, from any shell or CI, and fails a done with no exit-0 line behind it. No model is asked.
  4. The test has to fail once. adr-verify --mutant records whether the check noticed a broken build. None of the tools above asks that question.

Read 2026-09-24 from each tool's own README. If one of them ships these, open an issue and this box changes the same day.

Scope

Three design choices and the price, stated up front.

Each has a decision record or a measurement behind it in the repository. They are the shape of the tool, not gaps, and the last one is what it costs you.

  • The hooks are Claude Code. Cursor, Codex, Zed and Claude Desktop get the gates by path and a read-only MCP server (qh-mcp) that can tell you a record is dirty. Recording evidence needs a shell, because only a process that ran can write an exit code.
  • One refusal, on purpose. Once your project has a check, a command that names commit or push is refused until qh-check has passed on the tree (ADR-061). A warning a model treats as noise still publishes. Everything else advises and exits non-zero at most, so a CI step can read it.
  • It knows its own record shape. A MADR or Nygard file is reported as not-recognised and left alone (ADR-038). Bring new decisions to /quality-harness:adr-write; your old corpus is not judged.
  • The price. More turns: 2.33× on the README's own ablation, most of them cache reads. You write the acceptance command yourself; the tool will not guess it. The full mutation campaign is a CI and release job, about forty minutes on the plugin's own repository. Hooks run on every edit and start a Node process each time. claude plugin details quality-harness prints the context cost of the version you have.

Answers

Straight answers.

Is this just “write tests”?

No. Tests decide whether the code is right. This decides whether the claim that the work is done has a run behind it, and refuses the claim when it does not. The papers above measured the gap between those two things; this is aimed at the gap.

Why not have the model verify its own work?

Because the model is the thing being checked. Five LLM judges could not reliably detect false success (AUROC ≤ 0.65, arXiv 2606.09863). A model here may flag and exclude; only a program may record. adr-judge exists and is advisory by construction.

Does it block me?

One refusal, named above (ADR-061), with an opt-out. Everything else advises: it exits non-zero so a CI step can read it, and it says what to do next. A tool that stops you without saying why is worse than no tool, and that is written into the project's rules.

Can I run the checks outside Claude Code?

Yes. They are Python and Node programs under plugin/bin and plugin/scripts; run them by path from any shell, Makefile or CI job, with no model involved. Inside a Claude Code session they resolve by bare name.

Does it work with my language?

It has no opinion about your language or test runner. The acceptance command is whatever you type: go test ./..., pytest -k, npm test. That also means it will not guess one for you.
