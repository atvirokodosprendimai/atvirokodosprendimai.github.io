What the numbers say

Fewer turns, lower cost, the same solving as far as 191 tasks can tell.

four readings
  • Fewer turns, less time.
    With mrw the agent finished in fewer turns in every SWE-bench stage, on both models, and wall time fell with the turns. Folding many reads and edits into one call is what mrw is built for; the receipts count the turns, not which calls were folded.
  • Lower cost, most on Opus.
    The saving is largest where the agent works longest: Opus takes about twice Sonnet's turns per task, so there is more to fold. Stage 4b, 20 multi-hunk tasks on the same models, found the same: −20.9% [−32.3%, −8.6%] on Opus and −17.0% [−26.6%, −7.6%] on Sonnet.
  • Fewer tokens written, not always fewer read.
    Output tokens fell 29% on Opus and 24% on Sonnet. Total tokens fell 18% on Opus but rose 11% on Sonnet, and that rise is all cache reads (72k to 82k per attempt) while Sonnet's cache writes and output fell. Cost still fell on Sonnet, because cache reads are the cheapest tokens and the output that fell is priced far above them.
  • The same solving, as far as 191 tasks can tell.
    166 against 167 on Opus, 129 against 134 on Sonnet. Neither difference is significant; neither interval is narrow enough to prove there is no loss.
  • In short
    On these bug-fixing tasks mrw made Claude Code faster and cheaper, by about a fifth on Opus, and no measurement showed it solving less, though none was precise enough to show it does not.

How mrw is judged

The bar, and the verdicts against it.

Every stage is paired, pre-registered and graded against the bar in ADR-156. Each verdict is recorded in docs/bench/RESULTS.md exactly as bench analyze printed it.

the bar · ADR-156
  • PAYS
    The mean per-task cost down by 10% or more with its interval wholly below zero, and a solved-rate lower bound no worse than −5 points.
  • LOSES
    A cost interval wholly above zero or a solved-rate interval wholly below it.
  • INCONCLUSIVE
    Anything else.
the verdicts
  • Stage 5, Opus 5.5
    INCONCLUSIVE cost −19.4% [−25.5%, −12.7%]
  • Stage 5, Sonnet 5.5
    INCONCLUSIVE cost −7.0% [−12.1%, −1.8%]
  • Why not PAYS
    The cost intervals are 99% and lie wholly below zero. Solving is unchanged within what 191 tasks can show: the registered bar asks for a solved-rate lower bound no worse than −5 points, and the intervals reach −6.7 on Opus and −8.7 on Sonnet, so the recorded verdict is INCONCLUSIVE rather than PAYS; Sonnet's −7.0% is also short of the 10% mean saving PAYS asks for. Wall time was measured on a shared machine and is descriptive only.
  • Before SWE-bench
    Both Stage 5 verdicts were open when the stage ended at look 5 of 5. Before SWE-bench, four stages ran mrw on this project's own tasks (Stages 1, 1b, 2 and 4b, 24 to 40 tasks each, Sonnet and Opus): all INCONCLUSIVE, cost within ±3%. One stage went against mrw: Stage 4, 24 tasks chosen where mrw's mechanism should matter, on mrw v1.66.0, LOSES at cost +17.1% [+9.6%, +24.7%]. ADR-161 changed what mrw teaches in reply, and the rerun on v1.68.0 as Stage 4b came out INCONCLUSIVE on both models.

For anyone who wants to check.

where each claim is kept
  • Receipts
    One JSON per attempt under docs/bench/stage-5/block-1 … block-5, named <instance>.<config>.<model>.<repeat>[.rN].receipt.json; a .rN file is a retry of a run that did not finish and supersedes its base. Each carries the model, configuration, num_turns, wall_ms, total_cost_usd, usage by token kind, the harness verdict (oracle.harness_resolved), the size of the diff the agent produced (files, insertions, deletions) and the number of tool calls. The patch text was not kept: the attempt's worktree was discarded after grading.
  • Grader
    The official SWE-bench harness (swebench 5.0.2) on SWE-bench/SWE-bench_Verified, split test, dataset revision 78f471bf. The 191 instance ids and the rule that picked them are in bench/swe-bench/selection-adr-162.json.
  • Pre-registration
    The bar, the pool rule, the five looks and the stop rule were written in docs/adr/BACKLOG.md (“Pre-registered for ADR-162”) and in ADR-162, merged as 1fc00bad on 2026-10-17 at 08:42 UTC; the instance list was committed as 8b435f8f at 10:55 UTC; the first counted attempt started at 13:21 UTC the same day (started in its receipt).
  • Run setup
    run.json in each block: Claude Code 2.1.302, mrw v1.68.0 (975c3ba), a 1,200 s budget per attempt, one repeat, the same prompt and tool set for A and B. canary.json per block proves each configuration's setup before the block; exclusions.json names the one excluded attempt.
  • Verdicts
    docs/bench/stage-5/looks/look-5.txt, as bench analyze printed them, copied unchanged into RESULTS.md; ADR-162's acceptance fence diffs the two.
  • Independent scoring
    The paired rows were handed to the quality-harness project's own scorer, which reads them against its own pre-registration (its ADR-106).

Q&A

The SWE-bench result, question by question.

Numbers are Stage 5's (ADR-162, 2026-10-17 to 2026-10-21) unless a stage is named. Also in the repository: docs/bench/FAQ.md.

21 questions
What is mrw, in one sentence?

A Go CLI (and MCP server) that reads many ranges across many files and applies many edits across them in one call, returns a verdict for every edit, and refuses to edit a line it has not served you. MIT, one binary, no network call except mrw version --check-latest.

What exactly was compared?

A is Claude Code 2.1.302 with its own file tools: Bash, Read, Edit, Write, Glob, Grep. B is the same CLI with Bash and Glob, mrw v1.68.0 on PATH, and mrw instructions appended to the system prompt. Both arms also had Skill, as Stage 5's profile gives every configuration. Same task prompt, same model, same budget (1,200 s), same machine, one attempt per task per arm. So the comparison is “Claude Code's file tools” against “mrw as the file tool”. Configs in internal/bench/runner.go, the profile in internal/bench/profile.go; the prompt's SHA-256 in every block's run.json.

So you took tools away from B. Isn't the saving just fewer tools?

B lost Read, Edit, Write and Grep and gained mrw; that is the substitution being measured. B could still read through the shell (cat, grep), and did: 394 shell reads on Opus and 392 on Sonnet across 191 attempts each, counted and never refused (the “B shell reads” column in RESULTS.md). B wrote outside mrw in three Opus attempts (11 files in all, 9 of them in one attempt) and in no Sonnet attempt; every earlier stage had none. We did not run a “Claude Code minus tools, without mrw” arm; if the saving came from having fewer tools, B would be expected to solve less, and over the counted pairs it solved 165 against A's 166 on Opus and 129 against 134 on Sonnet.

It's cheaper. Why is the verdict INCONCLUSIVE and not PAYS?

The bar was registered before any run (BACKLOG.md, “Pre-registered for ADR-156”): PAYS needs the mean per-task relative cost (B − A)/A at −10% or lower with its interval wholly below zero, and the solved-rate difference's lower bound at −5 points or better. Opus met the cost half (−19.4% [−25.5%, −12.7%]) and missed the solved half (lower bound −6.7). Sonnet missed both (−7.0%, lower bound −8.7). 191 tasks give a solved-rate interval about ±7 points wide; a bound at −5 needs a narrower interval, which means more tasks. We report the verdict the bar gives, not the one we would like.

Why multi-hunk tasks? That is cherry-picking for mrw.

The pool rule was registered before the run: the 191 ids with the lowest sha256("adr-162:" + id) among SWE-bench Verified instances whose gold patch has at least two hunks, minus the ids earlier stages had used (bench/swe-bench/selection-adr-162.json, with the rule in the file). Multi-hunk is where mrw's one-call mechanism should matter, and the pre-registration says so. Stage 3, 20 random Verified instances with no hunk filter, also came out cheaper (−5.3% Opus, −6.1% Sonnet, n = 20, INCONCLUSIVE).

Show me the pre-registration.

ADR-162 and its BACKLOG entry merged as commit 1fc00bad on 2026-10-17 at 08:42 UTC; the instance list as 8b435f8f at 10:55 UTC; the first counted attempt started at 13:21 UTC (started in its receipt). The five looks, the stop rule, the 99% level and the exclusion rule are in that commit.

Who graded the patches?

The official SWE-bench harness (swebench 5.0.2) with its Docker images, run locally on every attempt. Each counted attempt's receipt carries oracle.harness_resolved, the harness's own verdict, beside the size of the diff the agent produced (files, insertions, deletions). The patch text itself was not kept: the attempt's worktree was discarded after grading. Nothing was graded by a model or by us.

Could the agent run the tests?

No. The checkouts the agent worked in had the code but not the test dependencies, so neither arm could check its own work; the harness graded afterwards in its own image. This holds for A and B alike, and it is the main limit of this stage: it measures bug-fixing without a feedback loop. Stage 6 (ADR-163) keeps the agent on the host and routes its Python and test commands through shims into a container of the instance's image, where the tests run.

Opus solving 167 of 191 looks high.

It is the single-attempt, no-test-run rate of Claude Code with Opus 5.5 on a multi-hunk subset; it is not a leaderboard number and we make no claim about it. The result is the paired difference: over the 190 counted pairs, 165 against 166 (166 against 167 over all 191 attempts).

What is “cost”?

total_cost_usd as Claude Code reports it per attempt, at October 2026 prices, cache tokens included. The runs were made on a Claude Code subscription, so no bill was paid per run; the figure is the CLI's own computed cost. Stage 5's A and B attempts together come to $109; every stage's A and B attempts, $228 ($245 with the pilots). The raw token counts (input, output, cache read, cache write) are in every receipt.

Why did Sonnet's total tokens go up?

Cache reads rose from 72k to 82k per attempt, while output fell 24% and cache writes fell. Our reading: mrw's appended instructions and its batched reads add to the context each call re-reads. Cache reads are the cheapest tokens; the output that fell is priced far above them, so cost fell 7% while the token count rose 11%. Opus fell on every kind.

Is “fewer turns” a real saving or an artefact?

A turn is num_turns as Claude Code reports it for the run. Opus 14.6 to 11.5, Sonnet 7.8 to 6.8. Our reading: each turn re-reads the context, so fewer turns is where the cost saving comes from; the receipts count the turns, not what each one did.

Wall time fell 40%. Is that real?

It fell with the turns (40% on Opus, 30% on Sonnet), but it was measured on one shared Apple Silicon machine, the SWE-bench images under amd64 emulation, beside other work, and it was not pre-registered. Treat it as descriptive. No verdict reads it.

What was excluded, and who decided?

The registered admission rule (BACKLOG.md, “Pre-registered for ADR-156”) allows two exclusions only: an attempt that died before its first tool call with an authentication, rate-limit or CLI start error, re-queued at most twice; and an attempt bench could not set up or grade. In A and B, one Sonnet attempt was excluded that way and re-queued (its .r1 receipt counted). One Opus A attempt (pytest-10051) was ended by the machine going to sleep; Zy ruled it infrastructure before the next look, and the ruling with the pmset log is in docs/bench/stage-5/exclusions.json, which is why Opus counts 190 pairs. Every excluded receipt stays on disk. An agent that gives up or runs past the 1,200 s budget is unsolved with its cost counted; three attempts (sympy-16597 in A and in B, django-16032 in B) were killed at the budget before the CLI reported any cost, so they count as unsolved and those two tasks leave the cost comparison, as look-5.txt says. Nothing else was dropped.

One run per task. Isn't that noise?

Yes, one attempt per task per arm; the pairing by task and 191 tasks are what give the interval its width. The intervals are 99% because the stage was read at five looks (ADR-162, Decision 5).

Does this hold for other agents or models?

Not measured. mrw runs under any shell, any MCP host and opencode; the numbers are for Claude Code 2.1.302 with Opus 5.5 and Sonnet 5.5 only.

What kind of work was measured?

One kind of work: a one-shot bug fix from an issue text, with no human in the loop and a 1,200 s budget. Long sessions, refactors and greenfield work were not measured on SWE-bench.

Earlier stages were worse. Why?

They are all published (RESULTS.md). Stage 4, 24 of this project's own tasks on v1.66.0, LOSES: +17.1%, driven by wide renames at +33%. ADR-161 changed what mrw teaches in reply (recipes first), and the rerun on v1.68.0 came out INCONCLUSIVE, cost within ±3%. The own-task stages have 24 to 40 tasks and nearly every task solved in both arms, so they could never show much.

RESULTS.md has a third configuration, P, that LOSES badly. What is it?

P is Claude Code with our quality-harness plugin, measured in the same stage: cost +49% on Opus and +70% on Sonnet, solved within one task of A (Opus 33 against 33 of 39, Sonnet 25 against 26 of 40), closed at the first look. The plugin is built for multi-step, recorded work with tests running; Stage 5 had neither, and its Stop hook kept attempts going in checkouts that could not run a test. It is a result about that plugin in that setting, and Stage 6 measures it where tests run.

How do I reproduce the table?

From a checkout, the jq command in the Evidence section regenerates the Stage 5 rows from the receipts; go run ./cmd/bench analyze --selection bench/swe-bench/selection-adr-160.json --selection bench/swe-bench/selection-adr-162.json docs/bench recomputes every verdict and interval. A full rerun needs Claude Code, Docker, the SWE-bench images (about 10 GB each), four days on one machine and about $110 of computed cost for A and B; bench run and ADR-162 describe it.

Install

One binary. No daemon, no account.

One call reads many ranges across many files; one call applies many edits across them, each with its own verdict. A plan that fails validation writes nothing, because a write that changed nothing is invisible.
